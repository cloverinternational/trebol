# Built-in Actions

Every name a window plugin can pass to [`tern.override`](api-window.md#ternoverride), [`cx:command`](api-window.md#window-cx) and [`tern.bind`](api-window.md#ternbind). Commands are the palette's rows; actions are the wider set of names the keymap runs, which includes every command.

## Names at a glance

| Name form | Example | `tern.bind` | `tern.override` / `cx:command` |
| --- | --- | --- | --- |
| Command id | `new_tab`, `layout:rail` | yes | yes |
| Keymap-only action | `palette`, `goto_tab:3`, `text:\e` | yes | no |
| View chord | `editor.toggle_comment`, `sqlite.write` | yes | no |
| Plugin command | `plugin.hello.say_hi` | yes | no |
| Plugin function bind | `plugin.hello.bind.0` | generated by `tern.bind` | no |

`tern.override` and `cx:command` accept only the [command ids](#commands) below: both look the id up in Tern's command list. Every other action name, including another plugin's `plugin.*` command, is rejected.

`cx:action(name)` runs every action-name form above immediately, not just commands.
View actions apply to the focused view. Unknown plugin actions raise rather than
silently doing nothing. Carly has the same action capabilities as a loaded window
plugin: built-in commands, keymap-only actions, focused-view actions and commands
from every loaded plugin.

## Commands

Tern has 173 built-in commands. The id is what `tern.override`, `cx:command`, `tern.bind` and `settings.json` `keybinds` take; the label is the palette row. Ids with a `:` are one command per value (`layout:rail`, `layout:float`, …); each value is its own id, and the bare prefix (`layout`) is not a command.

```lua
tern.override("split_right", function(cx)
	cx:toast("info", "Splitting")
	cx:command("split_right") -- runs the built-in; overrides are out of reach
	return true
end)
```

Every command can be overridden. The override is consulted at the top of the command's run, so it applies however the command starts: palette, key, menu, toolbar button, or another part of Tern. Commands that do nothing in the current context (for example `save` with no file block focused) still reach the override first.

### How overrides run

1. A command starts. If no loaded plugin has registered an override for its id, the built-in runs.
2. Otherwise each plugin's overrides for that id run in plugin order (plugins load sorted by id), each with a fresh window `cx`, as hook `override <id>`.
3. The first override that returns a truthy value stops the rest, and the built-in is skipped. A handler that raises or exceeds its budget counts as `false`; the failure is toasted.
4. If none returns truthy, the built-in runs.

While any plugin handler runs, the window's plugins are taken out of the window, so `cx:command(id)` from a handler runs the built-in directly: no override runs again and there is no recursion.

## Keymap actions

`tern.bind(chord, action)` takes any name in this section, any [command id](#commands), or a [plugin action](#plugin-actions). The name is parsed when the keymap is rebuilt, by the same parser as `settings.json` `keybinds`.

| Action | What it does | Notes |
| --- | --- | --- |
| `palette` | Opens the command palette | |
| `goto_tab:N` | Activates the session's tab `N` | 1-based; `goto_tab:0` and non-numbers don't parse |
| `last_tab` | Activates the session's last tab | |
| `focus_pane:DIR` | Focuses the pane in direction `DIR` | `left`, `right`, `up`, `down` |
| `resize_split:DIR` | Moves the nearest divider | `left`, `right`, `up`, `down` |
| `find_older` | Steps to the older find match | While the find bar is open |
| `find_newer` | Steps to the newer find match | While the find bar is open |
| `scroll_top_at_shell` | Scrolls to the top | In a terminal, outside full-screen programs |
| `scroll_bottom_at_shell` | Scrolls to the bottom | In a terminal, outside full-screen programs |
| `text:BYTES` | Writes `BYTES` to the focused terminal's program | Escapes `\e`, `\r`, `\n`, `\t`, `\\`, `\xHH`; any other escape doesn't parse |

`unbind` (and `[]`) is special to `settings.json` `keybinds`; it is not an action name, so `tern.bind(chord, "unbind")` is left out.

```lua
tern.bind("ctrl+alt+1", "goto_tab:1")
tern.bind("ctrl+alt+c", "text:\x03") -- send ^C
tern.bind("ctrl+a>%", "split_right")
```

## Plugin actions

A window plugin's [`tern.command`](api-window.md#terncommand) with id `say_hi` in plugin `hello` becomes the action `plugin.hello.say_hi`. The palette shows it by its `title`, in its `group` (default: the plugin's name). The action name can be bound with `tern.bind`, by any plugin, and in `settings.json` `keybinds`, and named by a status segment's `command`. It is not a built-in command, so `tern.override` and `cx:command` reject it.

A function passed to `tern.bind` gets the action name `plugin.<plugin>.bind.<n>`, `n` counting that plugin's function binds from 0. This is why `bind` is not allowed as a command id.

Any `plugin.<a>.<b>` with both parts non-empty parses, whether or not the plugin exists. When a key runs one, Tern finds the loaded plugin `<a>` and its command `<b>` (or function bind `<n>`); if there is none, nothing runs.

```lua
tern.command({
	id = "say_hi",
	title = "Say hi",
	run = function(cx)
		cx:toast("info", "hi")
	end,
})
tern.bind("ctrl+alt+shift+h", "plugin." .. tern.plugin.id .. ".say_hi")
```

See [Commands, Keys, and Overrides](../guides/commands.md) for a walkthrough.

## Chords

`tern.bind` chords are spelled as in `settings.json` `keybinds`:

- `+`-joined modifiers `ctrl`, `alt` (or `opt`), `shift`, `cmd` (or `super`), then one key.
- The key is a character as the layout types it (`ctrl+shift+2`, `cmd+plus`), a named key, `f1`–`f20`, or a physical key (`cmd+digit_1`, `ctrl+key_a`, `alt+bracket_left`).
- Sequences join chords with `>`: `ctrl+a>c` is ⌃A, then C. The chords before the last are a prefix.
- A modifier alone (`cmd`, `shift`, …) is its key tapped: pressed and released with nothing else. Taps go in sequences of taps only, each within half a second of the last: `shift>shift` is Shift twice (Tern binds `cmd>cmd`, ⌘ twice, to `carly`). Any other key or a click ends them.
- On Windows and Linux (and macOS with `swap_ctrl_cmd`), `ctrl` is the Ctrl key and `cmd`/`super` is the Windows or Super key.

Plugin binds sit above Tern's defaults and the keyboard preset and below the user's `keybinds`. Plugins only add keys: a bind on keys the defaults or preset already bind, or that starts or is started by one of their sequences, is left out.

## Errors

| Call | Bad input | Result |
| --- | --- | --- |
| `tern.override(id, fn)` | `id` not a command id | Raises ``tern.override: unknown command `<id>` `` |
| `cx:command(id)` | `id` not a command id | Raises ``unknown command `<id>` `` |
| `tern.command(def)` | `id` not letters, digits, `_`, `-`, or `bind` | Raises ``tern.command: bad id `<id>` (letters, digits, `_` and `-`; not `bind`)`` |
| `tern.bind(chord, action)` | `action` neither string nor function | Raises `tern.bind: the action is a name or a function` |
| `tern.bind(chord, action)` | chord or action name that doesn't parse | No error at the call. On keymap rebuild the bind is left out and the log gets a warning `plugin bind left out` with the parse error (for names, ``unknown action `<name>` ``) |
| `tern.bind(chord, action)` | keys the defaults or preset already bind | Left out; log warning `plugin bind left out: the preset binds these keys` |

`tern.bind` doesn't check that a `plugin.*` action exists; an unknown one parses and does nothing when pressed.
