# Memory retrieval iteration after live reload

## Before: observed failures

- Live `context_search("Where does a hypothetical non-existent quasar spool 934582 live?")` returned `candidate-leads` with five unrelated TaskManage Q&A records (Bash output, startup UI, renderer, capture, discovery). A direct source read showed the top Bash record answered a rendering question, not the hypothetical location. The candidate projection delegated to `ContextIndex.retrieve`, which counted generic query-word substrings (`.pi/lib/context/page-index-memory.ts#L58`).
- Live `memory_history(recall, scope=worktree, status=candidate, query=same hypothetical)` returned `status=ok` with three unrelated candidates, despite the agent's note saying no live calls had occurred and the leads were unverified. The agent had no explicit supported/no-support field.
- Live broad recall about the read-only memory agent sometimes returned `invalid-selection: Memory agent did not submit a selection`. The child receipt was deleted after the call; there was no detailed call trace. Short direct recall of `CapabilityManifestState.apply` selected the right TaskManage Q&A plus a meta lookup-progress record.

## Changes and observed post-change outputs

1. `.pi/lib/context/knowledge-pageindex.ts` now ranks distinctive query concepts, ignores common question words, omits unanswered questions and duplicate parent nodes, and requires multiple matched concepts for broad questions. A direct real-store projection for the **same hypothetical query** now returns `no-result`, not a candidate lead. `CapabilityManifestState.apply` still ranks TaskManage Q&A `48b544e64653fb3827c566999a17400e` first. This is a bounded lexical improvement, not semantic relevance proof.
2. `.pi/lib/state/memory-retrieval-worker.ts` now requires `memory_select({supported:boolean,selected,note})` and read-before-select. `.pi/lib/context/memory-agent.ts` returns `no-result` with empty knowledge when supported=false and rejects an inconsistent supported/selected envelope. Live isolated Pi worker invocation after the change selected **only** the relevant `CapabilityManifestState.apply` Q&A and returned it as a candidate; the hypothetical query terminated before the model with `no-result`. A second live query about memory-agent read-only tools selected three related candidate records, but they remain leads rather than validated implementation.
3. Injected selector outputs through the real parent selection boundary gave: supported=true/m0 → `ok` with the original Q&A ID; supported=false/[] → `no-result`; unknown ID → `invalid-selection` with “key not in offered snapshot”; duplicate m0 → `invalid-selection` with “repeats a card key”; provider failure → `model-failure` with empty knowledge. Reasons are fixed/bounded and never echo the child prompt or source body. The worker itself allows only `memory_browse`, `memory_read`, `memory_select`, and selected keys must have been read.
4. Direct candidate projection of `CapabilityManifestState.apply` kept the same ID, revision `d54c2d6ecb5fb594fc4d263b74272fcd`, worktree scope and candidate status. Verified-only projection returned `no-result`; the stored source record still has that candidate revision after the live read. No promotion or scope write was observed. Focused extension integration suites remained green (22 checks).

## Remaining limitation

This session's already-loaded `context_search` and `memory_history` tools still execute the **pre-edit extension instance** until another `/reload`; the post-change calls above used the updated library and actual isolated Pi worker directly, plus injected parent-boundary cases. Do not claim the active tool instance was hot-patched. A subsequent reload and calls to those two agent-facing tools are still needed to confirm the installed behavior end-to-end. A full child transcript/timeout was not captured; malformed/missing-receipt failures remain possible. The read-only agent sees at most 12 pre-ranked cards and cannot browse beyond them.
