# Pi in Tern: documented integration decision

Research snapshot: 2026-10-11. No implementation or live end-to-end test was performed. Read the [captured official mdBook](tern-site/MANIFEST.md), the [pinned SDK capture](tern-sdk/SOURCE-MANIFEST.md), and the [Pi integration map](tern-pi-integration-map.md) before using this as an implementation plan.

## Finding

**Use a Pi-side Tern Surface Protocol (TSP) renderer, not a Tern plugin that launches Pi RPC.** A program running in a Tern pane can send semantic UI frames over its existing pty; Tern renders them natively and sends input/events back over that pty (`tern-site/protocol/index.md`, `transport.md`). The docs explicitly name omp as such a program. Tern's TypeScript SDK supplies `connect`, an inline surface, keyed views, handlers, fallback detection, credit flow control, and an inline chat example (`tern-sdk/pages/typescript/README.md`). This route does not require changing Tern's closed native code or establishing an agent-backend registration API.

**Correction to the initial binary-only hypothesis:** Tern's native rendering of omp is documented as TSP, not evidence of Tern spawning omp over JSONL RPC. The exact args Tern uses when opening its *New agent* block remain unverified and are not necessary for a TSP-capable Pi executable. omp's separate JSONL RPC interface should not be confused with TSP.

## Options

| Route | Supported mechanism | Fit / limitation |
| --- | --- | --- |
| **Pi TSP renderer (recommended)** | Pi interactive entry runs in a pane; TSP SDK `connect({app: 'pi', features: [...]})`, `open({mode:'inline', role:'pi.session'})`, `render({main,dock,layer})`; fallback to Pi's existing terminal renderer when handshake fails. | Native transcript, controls, docked composer, streaming; one Pi process retains its own agent/session/tools. Implement as a selectable Pi renderer/mode, initially an experimental wrapper if Pi's internal session runtime can be imported safely. Requires adapter work and an actual Tern test. |
| Tern plugin block + Pi RPC | Host-side `tern.block.define` provides pane state, `view`, events, saved state (`tern-site/guides/blocks.md`). | `tern.process.run` closes stdin after a single payload and calls back only when the process exits; it captures bounded stdout/stderr (`tern-site/guides/io.md`). It cannot drive an ongoing JSONL RPC exchange directly. A persistent HTTP/socket bridge with `tern.fetch` and timers is possible as custom infrastructure but adds daemon/process supervision, restart, polling, and trust complexity. Do not choose it merely to acquire native views: TSP already gives those. |
| Native Tern backend | Change the Tern application itself. | Could integrate tightly with `cx.agents` but Tern application source is not in this repository. No public agent backend registration hook is documented. `cx.agents:start/ask/wait/...` controls existing agent blocks; `transcript` reads **omp.session** TSP chat and returns `{}` for non-omp agents (`tern-site/reference/api-window.md`, Agent cx; `tern-sdk/api/tern.d.luau:612-637`). TSP-rendered Pi is not guaranteed to become a fully supported `cx.agents` target or structured transcript without Tern changes. |

A small optional Tern **window plugin** can register a palette command to launch `pi` in a pane, but the renderer still belongs in Pi; a plugin is not the agent backend. Alternatively start it with `tern -e pi` / `tern new tab ... -- pi`, subject to normal Tern launch semantics. Investigate Tern's existing agent-command setting if the goal is the built-in *New agent* button rather than merely a native Pi pane.

## Contract

1. **Ownership.** Keep Pi's `AgentSession`/`SessionManager` and trebol extensions as the semantic and persistence authority (`vendor/pi-mono/packages/coding-agent/src/core/agent-session.ts`; `docs/reference/persistence.md`). A renderer subscribes to session events and projects messages, tool calls, thinking, statuses and extension UI requests into keyed TSP nodes. Do not mutate tasks, allow tools, or grant permissions merely because a node was clicked.
2. **Rendering.** Use `@stencil-hq/tern` pinned and tested against the installed Tern's v1 handshake. An `inline` surface has transcript `main`, composer/status `dock`, transient pickers and dialogs `layer` (`tern-site/protocol/surfaces.md`). Map text deltas to append operations where possible; maintain stable keys per message/tool; settle completed transcript subtrees and obey acknowledgements/retention (`tern-site/protocol/operations.md`). Use the documented `tool`, `agent`, `md`, `editor` and other element vocabulary (`tern-site/elements/work.md`, `input.md`). Avoid relying on `omp.session` role: it is omp-specific; test how generic Pi roles affect chat styling and agent discovery.
3. **Input.** Drive Pi's existing prompt/steer/follow-up/abort and model/session commands from TSP key and node events. A composer receiving `send` must atomically submit one prompt and report `sendable` only when Pi can accept it (`tern-site/protocol/input.md`). Implement `edit`/`undo` only if their corresponding event handlers really preserve text and undo; otherwise do not advertise those features (`tern-site/protocol/handshake.md`). Treat extension `confirm` dismissal, timeout and abort as deny, matching Pi's RPC handling (`vendor/pi-mono/packages/coding-agent/src/modes/rpc/rpc-mode.ts`).
4. **Lifecycle.** Keep Pi's normal session files; a TSP snapshot is display state, not persistence. Detaching a Tern window preserves a live daemon-owned pane; a daemon restart starts a new shell and restores old inline/flow surfaces closed/read-only (`tern-site/protocol/operations.md`). Resume the Pi session explicitly through Pi's own mechanism. On non-TSP terminals, tmux/screen restrictions, or handshake timeout, fall back to the existing terminal UI. Cleanly close the surface and restore tty on exit/signals (`tern-sdk/pages/typescript/README.md`).
5. **Version caveat.** Vendored pi-mono is 0.78.1 but the installed package reports 1.1.0 (`tern-pi-integration-map.md`). Before writing an adapter, choose the actual trebol runtime and check its internal session API. Do not assume a renderer can simply attach to a separately spawned `pi --mode rpc` process; that is a different architecture with extension UI and subprocess supervision responsibilities.

## Verification

- Run SDK `examples/chat.tsx` in installed Tern 0.5.3 and an ordinary terminal; verify native inline chat plus plain fallback, keyboard, mouse, and clean tty restoration.
- Build a minimal Pi event-to-TSP prototype against the *chosen* trebol runtime; test prompt, streaming text, tool progress/results, cancellation, session resume, and extension `select/confirm/input/editor` (including timeout/close denial). Verify trebol task state survives a renderer restart.
- Test detached/re-attached window, slow ack/credit starvation, settled/evicted nodes (`gone`), malformed TSP frame, process exit, and non-TSP terminal. Record/replay via `TERN_TSP_RECORD` and `surface-play` (`tern-site/protocol/operations.md`).
- Separately test whether the built-in agent block can launch this command and whether `cx.agents:list/ask/wait/transcript` recognize it. The docs explicitly say `transcript` is omp-only; do not promise parity there. A plugin palette launcher is the fallback if built-in registration is unavailable.

Open blocker: no live Pi/TSP prototype or confirmation of Tern's built-in *New agent* launch settings. This is a documented architecture recommendation, not a claim of working integration.
