# Ambitious native Tern experiences

Build the experience the user wishes existed, not the smallest text renderer that
satisfies a ticket. Interpret “overengineered” as exceptional interaction depth,
recovery, clarity and polish—not gratuitous architecture, decoration, or controls
without real behavior. A restrained appearance can hide extremely capable UX.

This is a repository-local skill. Keep it and its references here, tracked with
the project, rather than moving the instructions to a global autogenerated store.

## Mandatory discovery

1. Read AGENTS.md, current git status and the actual implementation. Preserve
   unrelated edits and re-check HEAD/status before finishing: concurrent merges
   can introduce files with names you intended to create. Never overwrite them.
2. Fetch https://docs.stencil.so/tern/index.md at the start of every Tern UI
   task to discover the latest published documentation. Follow its current links
   to guides/design.md, protocol/index.md and the element pages you will use;
   do not rely solely on remembered or copied documentation. If fetching fails,
   disclose that limitation and label any cached documentation as potentially stale.
   Check installed runtime
   support; documentation is not proof a particular binary supports a property.
3. Identify the authoritative state owner, current frontend, event path and input
   routing before drawing. Configuration, registration, active exposure, ongoing
   execution and successful completion are distinct facts.
4. Inspect native precedents: `.pi/lib/tern/mcp-{host,controller,panel}.ts`,
   `git-panel.ts`, `draft-edit.ts`, `bridge.ts`, `run.ts`, `tsp.ts`,
   `turn-groups.ts`, `work-summary.ts`, and adjacent tests. Reuse patterns, not
   their accidental constraints. Keep new behavior out of the giant bridge where
   a focused controller/projector or adapter belongs.

## Aim higher, with scope discipline

For every requested surface, inspect its neighboring journey: entry point,
selection, progressive disclosure, typing, searching, pending work, failure,
recovery, closing and return to chat. Proactively fix closely related friction
with a clear observable benefit. Do not wait for the user to enumerate every
missing hover state, shortcut, empty state or broken focus transition.

For material layout or workflow changes, enter plan mode and show alternatives
visually, recommend one, and resolve one decision at a time. Use visual_choice
when supported; the installed ask-user may instead require `questions` with
`type: preview` and per-option `preview` strings. Inspect its current schema
after a validation mismatch. Agree the scope before implementing a broad
redesign; separate useful adjacent improvements from unrelated rewrites.

The user explicitly wants ambitious upgrades to collapsed work and the user
input/composer. Use `references/work-and-composer.md` for the design checklist.
This preference does not authorize destructive actions or unsolicited changes to
unrelated systems. Preserve an explicit no-subagents request.

## Design native, not terminal text in a pretty wrapper

- Use TSP semantic nodes: overlay for a popup; table/list for selection; tabs for
  views; card for one selected object; stats for actual counts; field/input/editor
  for input; empty/skeleton/spinner for the respective states; toast for ephemeral
  confirmation. No ANSI box drawing, fake buttons or HTML dashboard imitation.
- Follow Tern's design guide: sans for people, mono for machine strings; semantic
  colors; quiet hierarchy; one contextual primary action; md toolbar controls
  and sm row/detail controls. CSS is a last resort, scoped and token-based.
- Progressive disclosure should preserve context. A compact state tells the user
  what matters; expansion reveals detail without losing their place. Never hide
  failures merely because successful steps are collapsed.
- Design loading, empty, unavailable, error, partial success, cancellation and
  success—not just a populated happy-path mockup. Provide a useful next action.
- Handle narrow panes, long identifiers, many rows, huge outputs and mixed
  success/failure. Use bounded scroll areas and stable keyed nodes. Avoid fake
  metrics, invented progress percentages and fabricated performance charts.
- Use Tern-owned animation and layout. Never run per-frame timers to simulate
  native spinners, elapsed time or transitions. Honor reduced motion.

## Interaction engineering

Write a small state machine or transition table before complex implementation.
Specify focus, keyboard owner, selection, disclosure, pending operation and
session generation. Overlay `modal: true` blocks pointer input, not PTY keys:
route BOTH native edit events and raw keys, bracketed/clipboard paste, undo,
send and Escape. A modal must not leak input into the chat composer.

Keep draft text, attachments, selection and caret intact when peeking at work or
closing a manager. Escape unwinds the innermost view first; display accurate
shortcuts. Test arrow keys, Unicode, selection, undo, copy/paste, multiline and
IME/native editing where supported. Do not advertise keys without handlers.

Preserve stable node IDs during streaming and status changes; replacing a fold
node can reset user collapse/scroll state. Do not auto-collapse a user's expanded
inspection or yank selection when a later event arrives. Keep follow-live an
explicit mode once the user has scrolled away.

Use one authoritative operation path. Native controls call existing runtime APIs
or a thin tested adapter, never a second backend or simulated command success.
Scope actions to stable IDs; confirm destructive changes against captured targets.
Guard duplicate submits, rejected actions, cancellation, stale session completion,
reload and unmount. Clean up subscriptions and visible-only polling. Closing a
panel does not prove an already-dispatched operation was cancelled.

Keep secret values out of summaries, logs, errors and persistent transcript
notices. A safe preview can name affected fields without their values. Drop
credential-bearing editor undo history on completion/cancel. Treat externally
provided labels as untrusted text and bound them without corrupting identifiers.

## Verification and iteration loop

1. Establish a baseline screenshot or reproduction of the actual complaint.
2. Add pure state/projector tests and bridge-level interaction tests—not just
   string snapshots. Cover loading/errors, late events, stale snapshots,
   selection retention, disclosure, multiple simultaneous runs and teardown.
3. Render through the real Tern engine. Use a deterministic fixture harness like
   `tools/e2e/tern-mcp-panel.mjs`, native element trees and screenshots. Inspect
   the images, not just their existence. Test wide and narrow panes and long data.
4. Exercise pointer and keyboard paths in a live owned pane when available.
   Headless screenshot replay proves rendering, not a live click→backend round
   trip. Simulated fixture success does not certify real OAuth or mutations.
5. Critique hierarchy, density, affordances, clipping, focus and recovery; iterate
   before calling it done. State concrete improvements over the baseline.
6. Run focused suites, affected full suites, typechecks and `git diff --check`.
   Run `npm run lint:tern`; distinguish baseline failures from new regressions.
   Never silently rewrite unrelated styles merely to make the gate green.
7. Update architecture/capability docs and changelog. Report exact tests, native
   screenshots, untested live paths, and reload versus restart requirements.
   Runner JavaScript changes require a pane restart; `/reload` is not enough.

## Definition of done

The interface is natively rendered and visibly reviewed, actions are real,
information is truthful, inputs are isolated, failure paths are recoverable,
state survives ordinary redraws, lifecycle resources are cleaned up, unrelated
work is preserved, and verification limitations are explicit. “Tests passed”
alone is not a UX acceptance criterion.
